# Contributing to ratchet

Thanks for wanting to help. ratchet writes to chips that decide whether a motherboard boots, so the bar is correctness first: a change that is honest about what it cannot do is better than one that looks finished.

## Ways to help

- **Report hardware results.** CI only exercises emulated hardware. A [hardware report](https://github.com/jackulau/ratchet/issues/new?template=hardware_report.yml) for a programmer, chip, or board you tried is one of the most useful contributions, whether it worked or not.
- **Report bugs.** Use the [bug report form](https://github.com/jackulau/ratchet/issues/new?template=bug_report.yml) and include the exact command and output.
- **Add a chip.** The database is [`rust/ratchet-core/data/chips.json`](rust/ratchet-core/data/chips.json). Take the values from the manufacturer datasheet and link it in the pull request.
- **Wire a protocol to live hardware.** The verbs marked *not wired* in the [README](README.md#status) have tested protocol logic and no live transport yet. Open an issue before starting one of these so the design can be agreed first.
- **Improve the docs.** Corrections and clearer wording are always welcome.

## Development setup

You need Rust 1.88 or newer, libusb-1.0, pkg-config, and libclang (bindgen uses it to generate the libusb bindings at build time).

```bash
# macOS (libclang comes with the Xcode command line tools)
brew install libusb pkgconf

# Debian / Ubuntu
sudo apt install libusb-1.0-0-dev pkg-config clang
```

```bash
git clone https://github.com/jackulau/ratchet
cd ratchet/rust
cargo build
```

No programmer is needed to develop. Set `RATCHET_FORCE_MOCK=1` to run the SPI flash commands against the in-memory mock backend (the I2C and JTAG verbs need a real programmer):

```bash
RATCHET_FORCE_MOCK=1 cargo run -p ratchet-cli -- status
```

## Before you open a pull request

Run what CI runs. From `rust/`:

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
RUSTDOCFLAGS="-D rustdoc::broken_intra_doc_links" cargo doc --workspace --no-deps
```

Then, from the repository root, the two smoke suites (they build a release binary if one is missing):

```bash
bash tasks/cli-smoke.sh
bash tasks/mcp-smoke.sh
```

CI also checks that the workspace builds on the minimum supported Rust version declared in `rust/Cargo.toml`, so avoid language and standard-library features newer than that.

## Project rules

These are the properties the project is built around. Pull requests that weaken them will be asked to change.

1. **No fake success.** A command with no live transport exits non-zero with a clear message. Nothing reports success for work it did not do, and nothing silently substitutes the mock backend for real hardware on a destructive path.
2. **Fail closed.** A short USB read, an unknown chip capacity, a set write-protect bit, or an implausible ID is an error, not a warning.
3. **Destructive paths stay guarded.** Backups, read-back verification, the blank-image guard, and the MCP `confirm` gate are defaults. New destructive operations need the same guards.
4. **No shelling out.** ratchet speaks the USB protocols itself. It does not wrap flashrom, avrdude, esptool, or similar tools at runtime.
5. **Tests come with the change.** Protocol logic is tested against the mock or the `LoopbackFlash` bus so it runs in CI without hardware. A bug fix includes a test that fails without the fix.
6. **Docs stay true.** If a change alters what a command does or which hardware it drives, update the README status tables in the same pull request.

## Repository layout

```
rust/
├── ratchet-usb-sys   libusb FFI bindings generated by bindgen
├── ratchet-usb       safe wrapper over the bindings
├── ratchet-core      chip database, backends, protocols, analysis, workflows
├── ratchet-cli       the `ratchet` binary
├── ratchet-mcp       the `ratchet-mcp` MCP server
└── ratchet-node      optional napi-rs bridge
docs/                 guides
packaging/            udev rules
tasks/                smoke suites used by CI
```

## Commits and pull requests

- Keep each pull request to one logical change.
- Write the commit subject as `type: what changed`, for example `fix: reads resume after a contact dropout`. The types in use are `fix`, `feat`, `perf`, `docs`, `test`, `ci`, and `chore`.
- Explain the why in the body: what was wrong, how you know, and how the change was verified.
- If the change touches a hardware path, say whether you ran it against real silicon, and on which programmer and chip.

Please do not open a public issue for a security problem. See [SECURITY.md](SECURITY.md).
